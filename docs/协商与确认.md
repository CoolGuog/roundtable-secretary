# 协商与确认（第 15、16 步）

对应任务清单第 15 条「多秘书协商」与第 16 条「全员确认与写入」。
实现范围：给出共同可用时间 → 提出方案 → 全员确认 → 写入各自日程。

## 接口

只用 GET / POST / PUT / DELETE（微信小程序的 `wx.request` 不支持 PATCH）。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/roundtables/:id/availability` | 计算共同可用时间 |
| GET | `/roundtables/:id/proposal` | 当前方案；没有方案时返回 **204** |
| POST | `/roundtables/:id/proposals` | 提出方案，body 为 `{ date, startTime, endTime }` |
| PUT | `/roundtables/:id/proposals/:proposalId` | 表决，body 为 `{ decision: 'ACCEPT' \| 'REJECT' }` |
| DELETE | `/roundtables/:id/proposals/:proposalId` | 提案人撤回待确认方案，返回 CANCELLED 方案；重复撤回幂等 |

`availability` 返回：

```jsonc
{
  "slots": [{ "date": "2026-10-01", "startTime": "09:00", "endTime": "10:00" }],
  "durationMinutes": 60,
  "window": { "dateFrom": "2026-10-01", "dateTo": "2026-10-03", "startTime": "09:00", "endTime": "18:00" },
  "coverage": { "shared": 2, "total": 3 },
  "reason": null,          // 无解时的原因
  "note": "还有 1 位成员未授权忙闲…"   // 有解但覆盖不全时的说明
}
```

## 隐私边界

1. 只有显式授权（`shareBusy=true`）的成员，其日程才参与计算。
2. 参与计算的只有起止时间，**标题、备注、个人记忆一概不读、不外传**。
3. 未授权成员的安排完全不参与计算，但结果会给出 `coverage` 与 `note`，
   避免把「部分人的空档」误当成「所有人的空档」。
4. 对外返回的方案投票只有「名字 + 态度」，不含 userId。

## 无解时怎么说清楚

`slots` 为空时，`reason` 一定非空，取以下三种之一：

- 成员不足两人：`圆桌只有一位成员，邀请其他人加入后才能协商共同时间`
- 无人授权：`还没有成员授权忙闲信息，无法计算共同时间`
- 有授权但排不出：`在 X 至 Y 的每日 HH:mm–HH:mm 内，找不到 N 分钟的共同空档，可以放宽日期范围或时段后重试`

宁可返回空列表加原因，也不给出一个看起来成立、实际没有依据的时段。

## 方案的状态与失效

- 一个圆桌同时最多一个 `OPEN` 方案，重复发起会被拒绝。
- 方案只接受当前候选里的时段：提出时会用最新的忙闲重算一遍，
  已经不成立的时段会被拒绝，防止拿过期信息发起确认。
- 超过 24 小时、活动开始时间已到，或圆桌 `version` 已变（成员加入、退出、被移除、有人改了授权）会使方案失效，不能继续表决。
- 读取当前方案或成功创建替代方案时，将旧的失效方案置为 `EXPIRED`，不需要先读取才能重新发起。数据库读取和状态更新共用事务，避免覆盖并发确认结果。
- 提案人可撤回 `OPEN` 方案，其他成员不能代为撤回。已确认方案不可撤回；重复撤回已取消方案不会写入日程。
- 当前方案优先返回待确认方案，否则返回最新方案，避免旧的已确认方案遮住新撤回或拒绝的方案。

## 写入日程

全员接受后，在同一个事务里：

1. 再次检查**每位成员**（含未授权成员）在该时段是否已有安排，有人冲突就整体放弃，
   提示「有成员在该时段已有其他安排，请重新选择时间」，不点名是谁；
2. 检查每人的日程容量，再为每位成员写入一条日程，标题取圆桌标题，`scope` 保持 `PRIVATE`；内存模式也会先验证整批，避免仅部分成员写入；
3. 方案置为 `CONFIRMED` 并记录 `appliedAt`。

幂等：方案已结束就不能再表决，也不会重复写入。有人拒绝则整体作废，需要重新发起。

## 已知边界

- 协商只看已授权成员的日程，不读取偏好与记忆，也不做「更偏好上午」之类的加权排序。
- 候选上限 6 个，每个空闲段最多 3 个，步长 30 分钟。
- 页面交互（点「提出 / 接受 / 拒绝」）需在开发者工具或真机手动验收。
