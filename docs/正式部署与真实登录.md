# 正式部署与真实登录

更新：2026-10-02。用户目前尚无服务器和域名，本轮完成部署代码与配置模板。公网部署、证书、真实微信换码和两个真实账号验收均未完成，不能按“已上线”交付。

## 部署结构与文件

首版采用一台 Linux 服务器，公网 HTTPS → Nginx → 127.0.0.1:3000 Node API → 本机 PostgreSQL。仅运行一个 API 进程；现有登录与模型限流是进程内状态，重启会清空，多实例需另做共享限流。模型初次部署设为 off，日程、记忆和协商仍可使用。

| 文件 | 用途 |
|---|---|
| deploy/production.env.example | 生产环境变量模板，真实值单独保存在服务器 |
| deploy/roundtable.service | systemd 服务、重启策略、低权限运行 |
| deploy/nginx.conf | HTTPS、请求体限制、每 IP 限流与简化访问日志 |
| deploy/nginx-proxy.conf | 代理超时、覆盖转发头、禁止自动重试写请求 |

生产启动必须设置 NODE_ENV=production、STORAGE_MODE=postgres、AUTH_MODE=wechat、实际 AppID/AppSecret、含密码的数据库地址、PUBLIC_API_ORIGIN。域名仅做格式校验，不能证明 DNS、证书或微信平台已配置。后台仅绑定 127.0.0.1；拒绝模拟换码与 stub 模型，演示登录入口返回 404。

API 登录总量为滚动一分钟 60 次、同时 4 次，失败也计数，超限返回 429。Nginx 登录接口另按 IP 平均每分钟 10 次、突发 5 次控制；共享网络可能共用额度。其他接口按 IP 每秒 10 次、突发 20 次。JSON 请求体上限 16KB。Nginx 模板应直接面向公网；若引入 CDN/负载均衡，需重新配置可信代理和来源地址，不能原样套用。

## 准备条件

准备支持 systemd 的 Linux 主机、可管理 DNS 的域名和 HTTPS 证书。安装受维护的 Node.js 22 或 24、npm、PostgreSQL、Nginx、Certbot，以及 Prisma 所需的系统 OpenSSL 运行库。以下示例采用 Debian/Ubuntu 常见目录；实际系统版本确定后再核对安装命令。主机与数据库需定期更新，并限制 SSH 来源；安全组开放 80/443，不开放 3000/5432。数据库 listen_addresses 保持本机，使用专用非超级用户。

域名解析到服务器后，按微信公众平台当时显示的主体、域名和备案要求完成配置。此文不保证购买某个服务器地区即可满足平台要求。

创建无交互登录的 roundtable 系统账号。约定目录：

```text
/srv/roundtable/releases/<发布编号>/  每次独立构建，包含源码与当前平台依赖
/srv/roundtable/current             指向当前发布目录的符号链接
/etc/roundtable/production.env      root 所有、权限 600，不放进发布包
/var/backups/roundtable/            限管理员访问，并加密复制到异机
```

服务账号对发布目录只需读取和执行权限，禁止修改代码。不要将 Windows node_modules 直接传到 Linux，Prisma 引擎须在目标平台生成。禁止把开发 .env、测试数据库、游客缓存或备份放入代码包。填完的生产配置也不提交 Git。

## 构建、备份与迁移

将已测试的明确 Git 提交放入一个新的发布目录。以普通部署账号构建；安装过程需要开发依赖，不要提前设置 NODE_ENV=production 或使用 --omit=dev：

```bash
npm ci --include=dev
npm run check
npm run build:api
```

创建 roundtable 数据库和专用账号，在安全的交互环境设置强密码。密码若含 URL 特殊字符，填写 DATABASE_URL 前进行百分号编码。复制模板到 /etc/roundtable/production.env，管理员在文件中填写实际凭证，权限设为 600。不要在聊天或终端命令参数中贴入凭证。

首次空库也记录备份基线；之后每次迁移前备份，不能使用 prisma migrate reset。以下命令由管理员在本机数据库环境执行，备份文件名每次使用新的发布编号：

```bash
sudo install -d -o postgres -g postgres -m 700 /var/backups/roundtable
sudo -u postgres pg_dump -Fc -f /var/backups/roundtable/RELEASE-before.dump roundtable
sudo -u postgres pg_restore --list /var/backups/roundtable/RELEASE-before.dump
```

确认 pg_dump 成功；--list 只证明目录可读，不等于恢复成功。还需把备份恢复到一个**新建的独立库**做恢复演练，检查业务表和数据。参考 [PostgreSQL 备份与恢复文档](https://www.postgresql.org/docs/current/backup-dump.html)。角色和密码配置需另外安全备份。

使用独立的一次性 systemd 任务加载生产环境执行迁移，避免把 EnvironmentFile 当成 shell 脚本 source。替换发布编号与已核实的 Node 路径，任务名每次唯一：

```bash
sudo systemd-run --wait --pipe --collect --unit=roundtable-migrate-RELEASE \
  --property=User=roundtable --property=Group=roundtable \
  --property=WorkingDirectory=/srv/roundtable/releases/RELEASE \
  --property=EnvironmentFile=/etc/roundtable/production.env \
  /usr/bin/node node_modules/prisma/build/index.js migrate deploy
```

迁移失败时不切换新版本，也不清空数据库。迁移输出按运维敏感日志保管。当前仓库六项迁移，本轮没有新增数据库迁移。

## 首次启动与 HTTPS

1. 确认 /usr/bin/node 指向受支持版本；若不同，同时修改 service 和迁移命令。
2. 创建 current 链接指向新发布目录。复制 roundtable.service 到 /etc/systemd/system/roundtable.service，执行 daemon-reload 和 enable --now。后续更新必须用 restart，enable --now 不会重启正在运行的服务。
3. 在服务器执行 `node scripts/check-api.mjs http://127.0.0.1:3000 --require-postgres --require-wechat`。须存活、就绪且微信模式；systemctl status 同时应正常。
4. 先只配置 Nginx 的 HTTP server 块及 `/.well-known/acme-challenge/` 目录，验证 DNS 和 80 端口，再申请证书。证书存在前不启用引用证书的 443 配置。
5. 替换 nginx.conf 中所有 api.example.com，复制代理片段至 /etc/nginx/snippets/roundtable-proxy.conf，安装完整配置到 /etc/nginx/conf.d/roundtable.conf。运行 `sudo nginx -t` 成功后再 reload。

证书申请示例（将域名替换为实际值；Certbot 的账户、邮箱与服务条款由管理员按实际情况设置）：

```bash
sudo install -d -m 755 /var/www/letsencrypt
sudo certbot certonly --webroot -w /var/www/letsencrypt -d api.example.com
sudo nginx -t
sudo systemctl reload nginx
sudo certbot renew --dry-run
```

设置并检查自动续期任务，续期成功后执行 `nginx -t && systemctl reload nginx` 的部署钩子。参考 [Certbot webroot 与续期说明](https://eff-certbot.readthedocs.io/en/stable/using.html#webroot)。模板限流参数依据 [Nginx limit_req 文档](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html)。模板尚未在实际 Linux/Nginx/systemd 环境运行验证。

从外部网络运行：

```bash
npm run check:api -- https://实际后台域名 --require-production
```

该命令同时要求 HTTPS、生产标记、PostgreSQL 和微信身份模式；失败返回非零退出码。/health 的 mode 沿用 local-wechat 字段以兼容旧客户端，deployment=production 才是生产标记。命令仅检查公开接口，不代表真实微信登录成功。

## 小程序与真实账号验收

后台部署通过后，保持项目 AppID 与 WECHAT_APP_ID 一致，在微信公众平台将 `https://实际后台域名` 配为 request 合法域名。若微信服务端接口还要求 IP 白名单，按控制台提示添加后台实际出口 IP。详情以公众平台和官方文档为准；不要关闭域名或证书检查来代替正式配置。

使用独立正式构建，无需修改本地开发配置（将地址替换为实际后台域名）：

```bash
npm run build:mini:release -- --api-origin https://实际后台域名
npm run check:mini:release -- releases/mini-实际生成的编号
```

将命令生成的独立目录导入开发者工具，用实际 AppID 编译；核对项目及本机私有设置中的域名校验均开启。构建自动设置 api/wechat/HTTPS 并保留文件校验清单，详见 [正式小程序构建](正式小程序构建.md)。上传体验版，由已获权限的两个真实微信账号在手机上验证。每一项记录时间、版本与结果，避免截图包含令牌或密钥。

| 验收 | 通过标准 | 当前状态 |
|---|---|---|
| 公网与证书 | Wi-Fi/移动网络访问，证书链与域名校验通过 | 待环境 |
| 实际微信登录 | wx.login → 后台官方换码 → 自建会话，个人页可读取 | 待验收 |
| 账号隔离 | A 新增虚构日程与记忆，B 无法查看或修改 | 待验收 |
| 持久化 | 退出重登及后台重启，A 仍能找回本人记录 | 待验收 |
| 退出失效 | 退出后旧令牌不可访问个人接口 | 待验收 |
| 协商 | 双方入房、授权、接受，双方各写入一次 | 待验收 |
| 真机异常恢复 | 断网、过期重新登录、失败重试无重复日程 | 待验收 |

任何真实 AppSecret、wx.login code、OpenID 和 session_key 都不发到聊天或文档。无效 code 返回 400；微信配置或上游异常返回 503；过量请求返回 429。排查时仅记录时间、HTTP 状态、配置检查结果与后台版本。微信登录流程参考 [官方说明](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/login)。

## 更新与恢复

新发布目录构建、备份、迁移成功后，记录旧 current 的真实目标和配置备份。在 /srv/roundtable 下创建指向新目录的临时符号链接，再用 `mv -Tf` 将它替换 current，随后 restart roundtable。必须先确认 current 是符号链接、目标位于 releases 内；不要用递归删除来切换版本。

若新代码验收失败且数据库结构兼容，切回已记录的上一个**支持生产模式**的发布目录并重启，再做只读检查。此前拒绝 production 的开发版本不能作为生产回退版本，不能通过切回 demo 身份恢复公网服务。首次上线失败应保持外部不可用并修复。

数据库不自动跟随代码回退。需要恢复数据库时，先停写、保留事故现场备份，再在新库恢复备份并验收，最后明确切换数据库连接；恢复会丢失备份之后的写入，需核对后单独决定。不执行 drop/reset 原生产库。

设置 /ready 失败告警、证书到期提醒、磁盘容量与备份失败告警、日志轮转和备份保留策略。公网发布前再核对这些运行项。代码备份不包含数据库和凭证，两者必须单独保存。
