# 双秘书协商 Demo

2026-10-16更新：新增用户自行设置的规则模板、可选日程名称读取授权与本人推荐理由。当前流程与隐私范围以[偏好规则与课程理解](偏好规则与课程理解.md)为准：未授权名称时仍只发送候选忙闲，授权后本人模型可读取日程名称和时间。以下原版两工具流程在未开启名称读取时仍适用。

本版目标：两位大学生的个人秘书分别读取本人的安排与偏好，交换候选时间，达成一致后提交双方确认。当前是两个逻辑独立的 Agent，共用后台配置的模型和 Key；并非每个用户已经接入自己的 API。

## 验收步骤

1. 启动 PostgreSQL 和后台，重新编译 demo-A、demo-B，两边使用不同的演示身份。
2. A、B 分别在“我的 → 管理我的记忆”记录偏好，例如 A“下午均可”，B“优先15点以后”。也可添加一个未来日期的课程作为冲突时段。
3. A 创建同一天 13:00—18:00、时长60分钟的课程讨论圆桌，B 用邀请码加入。选择尚未开始的日期。
4. 双方在圆桌详情授权本次忙闲，进入“让两位秘书协商”，各自点击“授权我的秘书”。模型将接收本人的候选忙闲和最多20条偏好／限制；不会读取 NOTE 备忘。
5. 由 A 点击“开始协商”。页面每3秒查询进展，显示真实工具调用和公开时间提议。模型结果不固定，也可能第一轮即达成一致。
6. 成功后双方返回圆桌，查看待确认方案。A 接受后，日程仍不应新增；B 也接受后，两人的日程才出现活动。
7. 再次协商需先完成或撤回已有待确认方案。每个圆桌两次启动至少间隔一分钟。

异常验收：未授权不可开始；普通成员不能启动；撤回秘书授权后停止后续处理；没有共同候选或模型失败时不写入日程；另一位成员看不到主人的课程标题和偏好原文。

## 实际执行流程

圆桌发起人启动 → 后台检查双方授权 → 生成未来候选时段 → A秘书选择工具动作 → 后台执行本人忙闲／偏好读取 → A提出时间 → B读取自己的工具结果并接受或提议其他时间 → 最多5轮 → 再检查双方日程 → 创建原有待确认方案 → 双方亲自接受 → 原有日程写入流程。

模型使用 JSON 工具动作循环，不是原生 `tool_calls` 协议。每次返回 `read_busy`、`read_preferences` 或 `answer`。后台负责验证和执行；模型不能指定 userId、读取其他人的数据、直接改日程或替主人投票。`read_busy` 返回每个候选是否可用，true为可用，false为冲突。工具结果已存在时模型应继续决策，不重复读取。

每位秘书有独立的模型上下文和本轮工具结果。相互交换的只有候选索引、接受／提议／拒绝状态。群内可读消息由程序根据真实动作生成，不直接展示模型自由文本或内部推理。偏好是模型决策参考，课程冲突则由后台硬校验；模型可能未能完全照顾偏好，最终由主人核对。

## 范围与安全边界

- 当前仅支持恰好两位成员，最多5轮，每位秘书每轮最多5次模型调用（包含工具读取及无效回答纠正）。全后台最多2个并发协商，单次协商6分钟总预算（正在等待的调用结束后检查），模型调用有独立超时。
- 按圆桌时间窗口、活动时长生成30分钟间隔候选，最多均匀抽取216个。无一致结果不代表不存在任何可行时间，可缩小日期范围或手动选时。
- 只发送本人候选忙闲和最多20条、每条最多200字符的偏好／限制，以及圆桌公开目标和时间反馈。Key仅供后台请求模型使用，不发送到小程序和协商消息中。模型服务商仍会收到被授权的数据，不能承诺“完全不会泄露”；生产上线前还需完善密钥托管、保留策略和隐私说明。
- 授权和过程仅保存在后台进程内，24小时失效，重启清空。圆桌成员或忙闲授权版本变化会使旧协商失效；撤回授权不能收回已发送给模型的信息。已生成的待确认方案需要在圆桌详情撤回。
- 日程、记忆和最终方案继续使用现有存储。本版没有新增数据库迁移，没有自动通知、后台持久任务或个人 Key 管理。
- 双方最终确认时沿用原有冲突检查与日程写入逻辑；秘书协商本身不保存任何日程。

```powershell
node scripts/check-agents.mjs
```

2026-10-13 实测：甲先提议13:00，乙根据虚构课程冲突及15点后偏好改提15:00—16:00，第二轮双方秘书达成一致；所有主人投票仍为PENDING，没有自动写入日程。

周末偏好验证可执行 `node scripts/check-agents.mjs --weekend`：虚构乙“尽量把娱乐活动安排在周六”，周六09:00—12:00有课；2026-10-13实测达成周六14:00—15:00方案。候选附有明确index和星期，活动标题与目标同时传给模型。“尽量/优先”为软偏好，应先寻找更符合偏好的替代时间；不因一次不满足软偏好立即退出。明确硬限制仍可拒绝。此测试不保证模型每次都会选择同一时间。

浮窗：每次触发只显示1秒，不自动重播。当前页面浮窗连续触发最多5次，第5次后进入30秒冷却；冷却内的点击不延长冷却。超过30秒未触发也会重置计数。冷却只抑制浮窗，不阻止按钮业务操作。

主要代码：`apps/api/src/agent-negotiation.ts`（授权与协商）、`apps/api/src/secretary.ts`（模型工具动作）、`apps/miniprogram/src/pages/agents/`（双秘书页面）。
