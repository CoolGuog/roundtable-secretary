# 重复日程与页面调整

## 已确认的规则

- 新增安排可选择“仅当天 / 每天 / 每周固定”。
- 每天重复需要结束日期，结束当天包含在内。
- 每周固定可勾选多个星期，从所选日期起生效，不要求结束日期。
- 编辑和删除重复安排时，先选择“仅本次 / 本次及以后”。删除还需二次确认。
- 仅本次改期会替换原时间，不会同时保留两条安排。
- 修改后续安排保留之前的历史，以及之后已单独修改、删除的例外；星期规则不变。后续修改的起点日期不能移动，单次修改可改日期。
- 停止本次及以后会保留之前的安排。当前没有提醒推送或跨午夜的重复安排。

## 页面变化

日程页的标题、刷新、搜索、分类、日期筛选、日程列表和添加入口属于同一个“个人安排”卡片。

秘书页的手动表单在“记一条个人安排”按钮下方展开。通过对话生成的草稿仍在对话区域之后确认。两个入口共用相同的填写表单。

重复安排默认展开最近 7 天到未来 30 天。选择具体日期、进入周视图或翻周会读取对应日期，远期重复规则仍然有效。普通单次记录继续可读，不因这个显示窗口被删除。

保存重复安排前检查起始日期至多 31 天内的个人安排冲突，需要用户明确选择“仍然保存”才可保留冲突。这个预检查范围不代表规则只有 31 天有效。

## 存储与协商

PostgreSQL 新增 `recurring_arrangements`，每条规则关联一个用户；规则、截止日期和单次例外以 JSONB 存储。通过已有会话验证读取和修改的用户，不能用其他人的 occurrence ID 修改课表。

服务只按查询日期展开，不向日程表无限插入每周记录。虚拟记录 ID 为 `r:<规则 UUID>:<原始发生日期>`；单次改期保留这个原始标识，原日期停止显示。

修改本次及以后时，在同一事务内截断旧规则、创建新版本。串行化事务遇到并发冲突会有限重试。新增规则使用保存请求编号，网络重试不会重复创建。单次日程仍使用原有表和流程。

圆桌计算读取授权成员的重复忙闲时段；最终确认在同一事务内检查全体成员实际活动日期的冲突。对其他成员只展示忙闲与协商结果，不公开课程标题或个人记忆。

本机演示模式使用单独的 `roundtable.demo.recurring.v1` 本地存储，API 模式使用服务器数据库。规则与修改版本每人合计最多 500 组，每组最多 500 个单次例外；一次显式读取的日期范围最多 63 天。

迁移已在本机数据库备份后应用，只新增表，未清空或转换旧日程。队友更新代码后执行 `npm.cmd install`、`npm.cmd run db:deploy`、`npm.cmd run check`，再构建小程序。数据库地址及密码仍使用各自未提交的 `.env`。

## 微信开发者工具验收

1. 在当前项目和 A、B 预览窗口分别点击“编译”。
2. 日程页确认筛选和列表位于同一卡片，秘书页点击手动新增确认表单位置。
3. 添加下周一开始的“课程”，08:30–10:00，每周一、三；不填写结束日期。
4. 用日期筛选查看周一、周二、周三，以及几个月后同星期日期；周视图翻周检查。
5. 仅修改一次课程时间，确认原时间消失、其他日期保持不变。
6. 从后续某天修改“本次及以后”，检查此前时间保留、之后更新。
7. 删除仅本次和删除本次及以后，分别验证取消确认不会删除、历史不会被清空。
8. 添加每天重复并选择截止日期，验证截止当天存在、下一天不再出现。
9. 两人圆桌安排到课程时段：已授权课程不应出现在共同候选中；未授权课程也应在最终确认时拦截冲突。

自动验证覆盖前后端类型检查、既有回归测试、真实 HTTP 的内存及隔离 PostgreSQL 合约、本机规则持久化、服务重启持久化、并发新增重试、用户隔离、圆桌冲突和表单操作。微信开发者工具的实际排版仍需按上述步骤肉眼验收。
