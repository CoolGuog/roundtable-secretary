# 日程保存与重试

更新日期：2026 年 9 月 30 日。

## 解决的问题

网络超时时，后台可能已经保存了安排。如果把用户的再次点击当成全新请求，就会产生重复日程。现在小程序为保存请求附带编号，后台按用户与编号识别重试；不会仅凭名称和时间删除或合并用户有意创建的相同日程。

## 接口规则

`POST /me/arrangements` 请求体仍为 `title`、`date`、`startTime`、`endTime`，可选请求头 `Idempotency-Key` 为 UUID v4。

- 同一用户、同一编号、相同内容：返回原日程，不新增；并发请求也只创建一条。
- 同一编号、不同内容：返回 409，不覆盖旧日程。
- 原日程后来编辑：原样重试返回当前日程，不将编辑还原。
- 原日程已删除：返回 409，不因迟到重试而重新创建。
- 不同账号的相同编号互不影响。接口不返回内部编号、摘要或所属账号。
- 原样重试在 100 条容量已满时仍能返回原结果；新建操作仍受容量限制。
- 不带编号的旧客户端保持原行为，没有重复保护；编号不是登录凭证，接口始终要求有效会话。

## 小程序行为与边界

API 模式下，同一运行期间、相同填写内容的未确认保存会复用编号；同时提交也共用编号。失败后用户可以先查看日程，再原样重试，客户端不自动重放写操作。成功收到结果后，下一次提交视为新的创建意图，使用新编号。

未确认请求仅保存在当前运行的内存中，不将 API 模式的日程正文缓存到本机存储。修改内容、退出登录或完全重启小程序后，不保证沿用此前编号：遇到不确定结果，先到日程页核对再创建。后台记录在 PostgreSQL 中持久化，即使后台重启，只要账号和编号相同仍能识别；内存演示模式的数据本来就不跨后台重启保留。

保存成功后先清空并关闭表单，再刷新日程数量。若只刷新失败，明确显示「安排已保存，数量暂未更新，无需再次保存」，不会将成功写入误报为失败。保存期间不能编辑表单字段。

## 数据库迁移

新增 `20260930010000_arrangement_create_requests`，只添加保存请求表及外键、索引，不修改或删除已有日程。

表中记录用户、请求编号、规范化内容的 SHA-256 摘要及关联日程 ID；不复制日程正文。日程与请求记录在同一可重试串行化事务中写入。删除日程后保留请求编号，关联 ID 置空；删除所属用户时级联删除该用户的请求记录。

部署前保存开发数据库备份，再执行 `npm run db:generate`、`npm run db:deploy` 并构建。回退旧版代码可保留新增表，不需要清空数据库或回滚已有业务数据。

## 验证

共享契约分别在内存与 PostgreSQL 模式验证并发重试、容量上限、用户隔离、内容冲突、编辑与删除、编号校验；数据库额外验证后台重启后仍识别原编号。小程序测试模拟响应丢失，检查手动重试沿用编号、成功后新请求换编号，以及保存成功后列表刷新失败的提示。

这些是接口和页面逻辑验证。原生按钮、真实微信账号与真机弱网操作仍需开发者工具和真机验收。
