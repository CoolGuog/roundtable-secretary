# 圆桌秘书：双人开发分工与流程

## 1. 开发目标与分工

首个完整版本围绕一个场景开发：两人或三人通过个人秘书，协商一次共同活动的时间，确认后写入各自日程。

| 人员 | 主要职责 | 主要工作目录 |
|---|---|---|
| A | 微信小程序、用户流程、前端联调、真机体验和演示材料 | `apps/miniprogram/src/` |
| B | 后台接口、数据库、个人记忆、模型调用、Agent 协商与安全 | `apps/api/src/`、`tests/` |
| 两人共同 | 接口约定、需求取舍、完整流程验收、AI Coding 过程记录 | `docs/` |

现有工程使用原生微信小程序与 TypeScript，后台使用 NestJS。后续数据库计划采用 PostgreSQL。

当前已完成个人日程演示骨架、类型检查、构建和 5 项后台测试；微信开发者工具中的页面渲染及真机体验仍待验证。真实微信登录、数据库、模型连接、多人协商尚未完成。

## 2. 开发流程与两人任务表

| 阶段 | A：小程序与产品 | B：后台与 Agent | 阶段交付物 | 共同验收标准 |
|---|---|---|---|---|
| 1. 跑通现有项目 | 导入微信开发者工具；检查秘书、圆桌、日程、我的四个页面；操作添加、查看、删除日程；记录布局和交互问题 | 安装依赖并执行检查；启动演示后台；确认身份隔离测试通过；整理现有演示功能的限制 | 问题清单、可运行的本地演示 | 添加一条虚构日程后能显示、保留和删除，页面无阻断问题 |
| 2. 约定接口和数据 | 梳理登录、个人日程、圆桌、方案确认四条页面流程；列出字段、按钮和异常状态；依据接口示例制作前端模拟数据 | 定义用户、日程、圆桌、成员、提案的数据结构；写出接口请求与响应、错误码及权限规则 | 接口文档、数据模型、页面清单 | 双方对字段含义、时间格式、身份和状态理解一致 |
| 3. 微信登录与个人日程 | 接入登录状态；日程页切换到后台接口；处理加载、失败、空列表与登录过期；落实 AppID 和测试账号 | 校验微信登录凭证；接入 PostgreSQL 和迁移；实现日程增删查改；所有操作根据后台会话识别所属用户 | 真实登录、持久化日程、访问权限测试 | 重启后台后数据仍存在；两个账号无法读取或修改彼此日程 |
| 4. 个人秘书与模型连接 | 做偏好和记忆管理页；做模型连接、测试连接、撤销连接及调用状态界面；做自然语言输入和保存前确认 | 建立个人记忆表；实现模型网关、密钥加密存储和日志脱敏；设置厂商白名单、额度与超时；把自然语言解析为待确认日程 | 单人秘书、模型连接、记忆编辑与删除 | 秘书能将自然语言转成正确安排；有歧义时澄清；确认后保存；密钥不返回前端、不进入日志或模型提示词 |
| 5. 圆桌房间 | 做创建圆桌、邀请码加入、成员列表、活动需求和本次授权设置页面 | 实现圆桌与成员管理、邀请码有效期和访问权限；保存活动目标、授权范围与协商状态 | 可加入的活动房间、授权记录 | 两个账号能进入同一圆桌；非成员不可访问；成员只能看到获准共享的信息 |
| 6. 多秘书协商 | 展示各秘书公开结论、候选方案、冲突原因、调用失败和重新协商入口；准备有解与无解的测试场景 | 各秘书只读取本人的授权信息；生成忙闲与偏好摘要；主持逻辑计算候选时间，模型辅助解释与权衡；限制轮数、调用次数和费用 | 可运行的多秘书协商流程 | 有交集时提出符合硬约束的方案；无交集时明确说明；不会泄露私人安排标题或原因 |
| 7. 确认与写入日程 | 做方案详情、同意、拒绝、修改建议、最终结果和变更提示页面 | 实现带版本的确认状态；全员确认后检查冲突并写入日程；处理重复请求、过期提案和活动变更 | 完整活动闭环 | 重复点击不会重复写入；方案变化后旧确认失效；未获全员确认不自动定案 |
| 8. 测试与参赛交付 | 完成真机和弱网测试；修复体验问题；录制演示；整理用户故事、创新点和操作说明 | 测试越权、提示词注入、密钥与隐私泄露、模型失败及并发；整理部署、架构和安全说明 | 可演示版本、视频、说明书、AI Coding 过程材料 | 两个账号能稳定完成发起、邀请、协商、确认、生成日程的全过程 |

阶段按依赖顺序推进。每一阶段内，A 可以依据接口示例先开发页面，B 同时实现后台；阶段结束后必须使用真实接口联调。

## 3. 第一轮具体任务

### A：验证小程序并整理页面需求

- [ ] 在微信开发者工具中导入 `D:\万象无限\roundtable-secretary`。
- [ ] 按工具要求使用测试号或自己的小程序 AppID。
- [ ] 检查四个页面能否打开，文字、输入框和按钮是否正常显示。
- [ ] 添加一条虚构日程，切换页面查看，重新打开后检查，再删除。
- [ ] 记录每个问题的操作步骤、预期结果和实际结果。
- [ ] 列出下一阶段登录页、日程编辑页需要的字段和状态。

### B：验证后台并起草接口约定

- [ ] 在项目根目录执行 `npm.cmd install` 和 `npm.cmd run check`。
- [ ] 执行 `npm.cmd run start:api`，检查本机演示后台是否可用。
- [ ] 阅读现有会话与日程接口，明确演示登录不能用于正式部署。
- [ ] 起草用户、日程和个人记忆的数据模型。
- [ ] 写出登录、日程增删查改接口的请求、响应及错误示例。
- [ ] 准备 PostgreSQL 开发环境与数据库迁移方案。

### 两人第一次联调

- [ ] A 按运行说明切换到 API 模式并重新构建小程序。
- [ ] 验证小程序能通过本机后台新增、读取和删除日程。
- [ ] 对齐下一阶段接口文档，并确定共同使用的日期、时间和时区规则。

API 演示模式仅适用于开发者工具模拟器连接电脑本机后台。手机的 `127.0.0.1` 指向手机自身，不能直接用这个地址进行真机后台联调。

## 4. 并行开发前必须确定的约定

| 项目 | 约定 |
|---|---|
| 用户身份 | 后台从会话识别用户；前端传入的用户 ID 不能作为访问权限依据 |
| 日程数据 | 明确标题、起止时间、时区、所属用户和可用于协商的范围；首版统一使用北京时间，并明确跨日安排的处理方式 |
| 个人记忆 | 按用户隔离；保留来源与更新时间；用户可以查看、修改和删除 |
| 信息交换 | 只交换本次活动授权的忙闲摘要和必要偏好；公开内容生成后仍需后台权限规则过滤 |
| 模型凭证 | 提交后清除输入框，不写入前端持久存储；后台加密保存，页面只返回连接状态和必要的脱敏标识 |
| Agent 权限 | 模型提出建议；后台负责校验权限和参数；模型输出不能直接绕过规则修改数据库 |
| 最终决定权 | 主持逻辑提出方案，各真人确认；写入前重新检查方案版本和日程冲突 |
| 错误处理 | 统一处理登录失效、无权限、输入错误、网络失败、模型超时和额度不足 |
| 主持调用费用 | 明确使用哪一方凭证或平台预算；首版可由发起人授权主持调用，界面提前说明；禁止自动借用其他成员的密钥 |

## 5. 协作与验收方式

每轮可以安排为“各自开发 2～3 天 → 合并联调半天 → 修复问题半天”。这是协作节奏建议，具体进度按实际问题调整。

1. 开工前：一起明确本轮用户能完成什么操作，并更新接口文档。
2. 开发中：A 维护页面与前端服务，B 维护后台和数据模型。接口变化先通知对方，并同步示例。
3. 合并时：先通过类型检查和相关自动化测试，再使用两个账号走完整流程。
4. 验收时：记录通过项、失败项和未测试项；未完成真实联调的功能不标记为完成。
5. 全程：两人分别保存 AI 辅助需求分析、设计、编码、审查和测试的过程材料，清除密钥、令牌和私人数据后归档。

建议使用同一个 Git 仓库，每个功能单独分支；合并前由另一人检查。数据库迁移和接口变更需要在合并说明中明确标注。

## 6. 最小版本范围

优先完成：个人日程、少量偏好、个人模型连接、两到三人圆桌、共同时间协商、全员确认、写入日程，以及小程序内可查看的结果通知。

地点先采用成员提供的候选项。外部地图搜索、自动预订、多种日历同步、连接外部 Agent 软件和复杂长期记忆作为后续扩展。微信订阅消息需在条件具备后单独接入和验证，不作为首个演示闭环的前提。

## 7. 里程碑检查

- [ ] M1：微信开发者工具中能正常操作个人日程。
- [ ] M2：微信登录和数据库可用，两个用户的数据相互隔离。
- [ ] M3：用户连接模型后，个人秘书能生成待确认的安排。
- [ ] M4：多人加入圆桌后，秘书能提出共同可行方案。
- [ ] M5：全员确认后生成日程，完成测试与参赛材料。
