# 会议复盘与责任分配

更新日期：2026 年 10 月 6 日。

会议未能举办时，由发起人记录事实与责任建议，各成员独立确认或提出异议；全员同意后才显示「已达成共识」。责任比例由人提出，系统不会根据缺席、拒绝时段或忙闲信息自动判责。

## 怎么用

1. 进入「圆桌 → 某个圆桌 → 记录原因／查看复盘」。已关闭的圆桌也能复盘。
2. 发起人填写圆桌日期范围内、今天或之前的会议日期，选择「未能举办」或「已取消」，描述经过和依据。
3. 为每名参与者提出 0—100 的整数责任比例。非零比例必须有依据，可补充具体补救事项；外部原因大于 0 时也须说明。
4. 成员责任、外部原因、待查／尚未分配合计必须为 100%。不清楚的部分可以暂留待查，不必强行分给成员。
5. 后台模式提交后，每位参与者分别确认最新版本，或写明异议。发起人提交本身不算确认。有人异议时显示「存在异议」，没有默认确认或超时自动归责。
6. 发起人核对后修订，会新增一版并将所有表态重置为待确认。旧版事实、比例、异议与表态记录仍可查看。

例如：发起人 40%、另一名成员 20%、外部原因 20%、待查 20%。第二位成员说明已提前完成约定，发起人核对后可以把其责任改为 0%，把未查清的部分移入待查，再请所有人重新确认。

「已达成共识」只代表参与者同意当前记录；如果仍有待查份额，会明确显示这部分尚未归属。确认后也可以提出新异议，状态重新变为存在异议，旧确认不会被删除。

## 本机与后台的区别

| 模式 | 可用行为 | 边界 |
|---|---|---|
| 本机 local | 写复盘草稿、分配本人／外部／待查份额、记录补救、修订与查看历史 | 当前本机圆桌只有本人，不显示多人确认按钮，保存始终是「本机草稿」 |
| 后台 memory | 多个演示账号提出、确认、异议、修订 | 仅供本机联调；后台重启清空内存数据 |
| 后台 postgres | 同样的多人流程，复盘和表态持久化 | 需应用新增迁移；真实微信登录和跨设备验收尚未完成 |

本机草稿不会自动上传或导入后台。事实依据目前是文字描述，不支持上传证据附件；系统不验证文字是否属实。补救事项目前是复盘记录，不会自动创建日程或任务。

## 确认、历史与权限

- 只有圆桌发起人可以提出或修订。接口按会话识别表态者，不接受客户端代填他人身份。
- 第一版复盘保存当时的圆桌成员成为固定参与者。移除成员不会抹掉其责任与异议，也不能通过修订把该参与者删掉。后加入者不能替原参与者确认。
- 已离开的参与者无法访问圆桌；其表态会保留。若以同一账号重新加入，可以继续本人表态。参与者名单来自首次复盘时的圆桌，不等于系统验证过的实际参会名单。
- 所有当前圆桌成员可以读取复盘；敏感的私人日程和记忆不会被系统自动加入复盘。
- 每次修改和表态都检查版本号。旧页面、重复提交或并发操作遇到新版本返回冲突，不能覆盖他人最新结果。读取失败时暂停写入，填写内容保留；不会自动重发写操作。
- 每圆桌一份复盘，最多 20 个修订版本；每版最多 100 次表态，整份后台记录最多约 250KB。达到容量上限拒绝本次操作，保留已有历史。本机另限 100 份草稿、单份 80,000 个序列化字符。
- 复盘不改变会议原方案或任何人的日程，不执行处罚、扣款或对外发布。没有定时提醒、推送通知或自动仲裁。

## 后台与迁移

新增接口：

| 方法与路径 | 用途 |
|---|---|
| `GET /roundtables/:id/review` | 读取参与者、当前版本与修订历史 |
| `PUT /roundtables/:id/review` | 发起人提出／修订，必须携带读取到的 `version` |
| `PUT /roundtables/:id/review/vote` | 本人确认／异议，必须携带当前 `version` |

新增迁移 `20261005010000_meeting_reviews`，只增加 `meeting_reviews` 表，通过外键关联圆桌；不改写旧业务数据。启动与 `/ready` 会检查该表。

本轮只在随机独立的本机 PostgreSQL 测试 schema 应用了迁移，**没有迁移主项目数据库**。当前 local 模式不受影响。之后要运行 PostgreSQL 后台时，先按现有备份流程备份数据库、确认 `.env` 指向正确的本机数据库，再运行：

```powershell
npm.cmd run db:deploy
npm.cmd run build:api
```

回退源码不需要删掉新增表；保留表中的复盘数据，再切换旧代码。恢复包只包含源码，不包含数据库、微信缓存、凭证或 `.env`。不要用清理缓存或删除表代替代码回退。
